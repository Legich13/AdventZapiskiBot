# Виджеты Telegram и утренняя доставка

В личном чате бот принимает `POST /telegram/webhook`. `TelegramWebhookRequest` проверяет секретный заголовок, структуру обновления и передаёт типизированное событие в `HandleTelegramUpdateAction`. Неиспользуемые типы Telegram Update получают HTTP 204. Когда Telegram явно ограничил доставку ответа на `/start`, webhook возвращает 503 с `Retry-After`. Повтор обновления продолжает выдачу оставшихся сообщений. Для запросов виджета проверяются получатель, частный чат и привязка номера сообщения. Утреннее сообщение допускает открытие только своей даты.

## Первое получение и повтор команды /start

Приветствие отправляется через `NutgramGateway::welcome` как статический `sendWidget`: красная карточка переиспользует стили, гирлянду и подарок календаря. `WidgetRenderer::renderWelcome` возвращает `RenderedWidgetDTO` без чтения календаря и БД. Подпись пуста, `allow_queries` выключен; карточка не вызывает `state` или открытие подарков и не создаёт `WidgetMessage`.

Встроенная золотая ссылка «Создать календарь» использует `services.telegram.mini_app_url` из `TELEGRAM_MINI_APP_URL`. Значение по умолчанию — `https://t.me/AdventZapiskiBot?startapp`. В BotFather главная Mini App этого бота должна указывать на `https://prokitap.ddns.net/app`. Обычный HTTPS-адрес редактора не заменяет Telegram-ссылку: вход по-прежнему проверяет подписанный `initData`. Перед выпуском нужно проверить открытие редактора из карточки в клиенте Telegram.

Мастерская показывает выбранному профилю тот же шаблон в изолированном `iframe` с экранированным `srcdoc` и локальной ссылкой `/app`, открывающей верхнее окно. Для предпросмотра не нужны календарь и запись сообщения. Транспорт, тексты, ссылка и лимиты HTML проверяются в `TelegramWelcomeWidgetTest`, локальный просмотр — в `StudioTest`.

При первом получении команды `PrepareStartUpdateAction` сохраняет Telegram ID и список вручённых календарей для данного `update_id` в таблице `telegram_start_updates`. Проверка ника, вручение, снятие прежней блокировки бота и сохранение списка проходят в одной транзакции PostgreSQL. Новая команда получает свой список. Повтор того же обновления использует исходный список даже после смены ника или появления новых календарей. Блокировка, возникшая между попытками, сохраняется.

Перед обращением к Telegram обработчик резервирует позицию в `telegram_start_messages`. Нулевая позиция соответствует приветствию, остальные идут по сохранённому порядку календарей. Подтверждённый отказ 429 освобождает позицию для повторной отправки. При неопределённом результате резерв остаётся в базе.

Параллельный запрос с тем же `update_id` получает 503 и `Retry-After: 3`, пока выполняется первая отправка. Блокировка принадлежит соединению PostgreSQL до завершения обработки или отключения процесса. Сетевой вызов Telegram выполняется после фиксации транзакции с вручением. Смену владельца ника, очистку кеша, два последовательных отказа 429 и пересечение двух процессов проверяет [TelegramStartReplayTest](../../backend/tests/Feature/TelegramStartReplayTest.php).

## Что хранится в PostgreSQL

| Модель | Правила записи | Проверка |
|---|---|---|
| WidgetMessage | Подтверждённое сообщение связано с календарём и получателем. Для утренней карточки записана дата. В локальном чате сохраняется точный HTML без текстов подарков. | Тесты привязки старого сообщения, авторизации и ограничения размера HTML в TelegramWidgetTest |
| MorningDelivery | Уникальная запись на получателя и дату. Прочтение записки и подтверждение доставки хранятся независимо. | Тесты границы 10:00 МСК, недоступного адресата и повторного задания |

Для подготовки сценариев используются фабрики WidgetMessageFactory и MorningDeliveryFactory. Календарь и получатель фабричной записи связаны; для конкретного сценария задайте явные внешние ключи. Продуктовый доступ к сообщениям и доставкам проходит через контракты WidgetRepository и MorningDeliveryRepository. Провайдер связывает их с EloquentWidgetRepository и PostgresMorningDeliveryRepository. Сервисы возвращают DTO и скаляры, не передают конструкторы запросов в интерфейсы.

## Очередь

`calendar:morning` с 10:00 МСК резервирует получателей с сегодняшним подарком, включая уже открытые дни и позднее вручение. Время `claimed_at` должно быть задано и не превышать текущее время `GiftClock`. Тот же `DispatchMorningRemindersAction` вызывается для конкретного получателя внутри первой публикации себе и новой обработки /start после снятия отметки блокировки бота. Резерв доставки фиксируется вместе с публикацией или вручением, а `SendMorningGift::dispatch()->afterCommit()` передаёт задание PostgreSQL-воркеру только после внешнего коммита. Откат отменяет резерв и задание. Повтор команды и пересечение с планировщиком сохраняют одну доставку на получателя и дату.

Минутный планировщик подхватывает сегодняшнюю доставку при пропуске непосредственного запуска. Через пять минут он сверяет ожидающую доставку с живыми заданиями PostgreSQL по идентификатору доставки. Если задание потерялось, планировщик создаёт его заново. Задания, оставшиеся в очереди при обновлении приложения, распознаются по сохранённому полю `deliveryId`.

Воркер загружает состояние календаря и готовит HTML в статусе `pending`. Временная ошибка чтения или рендеринга оставляет доставку доступной для повторной попытки. Непосредственно перед вызовом Nutgram один воркер переводит запись в `sending` атомарным обновлением. Позднее подтверждение Telegram уточняет исход зависшей отправки. Номер сообщения и статус `sent` фиксируются в общей транзакции.

При ответе Bot API 429 воркеры сохраняют под общей блокировкой наиболее позднюю дату окончания паузы из полученных `retry_after`. Задание возвращается в очередь с задержкой. Блокировка бота завершает отправку со статусом blocked. Новый /start снимает блокировку. При неопределённом сетевом исходе сохраняется unknown и автоматическая повторная отправка исключается.

Внешний вызов выполняет NutgramGateway. Локальный просмотр и тесты используют те же построитель HTML, серверную проверку даты и обработчик открытия подарка.

В мастерской дата подарка, порог 10:00 и текущее время вручения берутся из GiftClock. Публикация себе и /dev/start запускают ту же доставку; скрытое время передаётся воркеру штатным Context очереди. Срок жизни блокировок, очередь и интервалы повторных попыток отсчитываются по системным часам. На одного получателя разрешены пять запросов состояния и пять попыток открытия за пять секунд. Фоновые обновления карточек расходуют лимит запросов состояния.
