# Архитектура адвент-календаря

## Приложение и данные

- **ARCH-CALENDAR-001**. PostgreSQL хранит текущих пользователей Telegram, календари, дни с записками, первые открытия, связь с сообщениями и результаты отправки. Уникальность получателя в месяце и резервирование утреннего задания обеспечиваются ограничениями базы. Привязанный календарь принадлежит постоянному Telegram ID.
- **ARCH-CALENDAR-002**. Получение календаря, публикация и первое открытие выполняются на сервере. Один обработчик открывает подарок из календаря и из утренней карточки. Дата определяется в Europe/Moscow, время доставки отделено от времени доступности.
- **ARCH-ACCESS-001**. Mini App аутентифицирует сессию через проверенный Telegram initData. Обработчик webhook проверяет секрет, участника и привязку сообщения. Только автор управляет черновиком, получатель открывает подарок, сотрудник с правом панели видит состояние выдачи и доставки.
- **ARCH-TELEGRAM-001**. Виджеты получают компактное состояние и текст только запрошенного доступного подарка. Laravel Scheduler и очередь в PostgreSQL инициируют доставку. Неопределённый исход отправки требует отдельного учёта.
- **ARCH-LOCAL-001**. Эмуляция Telegram доступна в локальном окружении. Тестовые действия вызывают те же операции Laravel и рендерят те же виджеты, что и в боевом боте. Сессии пользователей и тестовое время изолированы.
- **ARCH-PLAN-001**. Изменения поведения начинают с падающей целевой проверки. Этапы и проверенные результаты записываются по FAST_STRICT/2. Перед сдачей проверяются код, границы авторизации, данные, интерфейсы и доступность.

## Где живёт код

| Граница | Обязанность |
|---|---|
| Route и Middleware | Выбрать контроллер, сессию и ограничения частоты. Контекст среды проверяется до вызова use case. |
| Form Request и Policy/Gate | Проверить форму, формат, пользователя и разрешение. Серверная операция повторно проверяет бизнес-инварианты в транзакции. |
| Controller и Filament Page | Передать типизированный ввод Action или Service и отдать Response, Resource либо Blade. |
| Action | Выполнить один переход. Например, опубликовать календарь, открыть подарок или зарезервировать отправку. |
| Service | Построить read-модель или выполнить вычисление. |
| Contracts и Infrastructure/Persistence | Предметный контракт находится в модуле. Реализация запрашивает PostgreSQL, загружает данные и формирует DTO. |
| DTO и Resource | Неизменяемое значение между слоями и явный публичный набор полей на выходе. |
| Job и Infrastructure | Job передаёт устойчивый идентификатор в Action. Адаптер владеет вызовами Nutgram и переводит ответы транспортного уровня. |

Запись проходит от Controller к Action и Repository, чтение — от Controller к Service и Repository. PostgreSQL подтверждает владение, открытия и резервирование отправки. Продуктовые запросы сосредоточены в репозиториях. Выборка полей автора и представление получателя имеют разные границы доступа. Blade получает готовую модель чтения, представление виджета получает состояния дат, а текст запрашивается при открытии.

### Правила Jobgram, применимые к календарю

- [ARCH-MOD-001] [MUST] Зависимости направляются от delivery/UI к application/domain, затем к явно выделенной infrastructure/persistence границе.

- [ARCH-MOD-002] [MUST] Бизнес-правило имеет одного владельца. Остальные слои вызывают его, а не дублируют.

- [ARCH-MOD-003] [MUST] Публичные контракты явны: типы, HTTP Resources, API-схема, ошибки и события не выводятся случайно из внутренней модели.

- [ARCH-MOD-004] [MUST] Новая абстракция появляется только при существующей границе, сменяемой реализации или повторяющемся поведении.

- [ARCH-MOD-005] [MUST NOT] Создавать интерфейс на каждую модель, универсальный CRUD-репозиторий или новый слой «на будущее».

- [ARCH-MOD-006] [MUST NOT] Обходить владельца слоя ради более короткого импорта или прямого запроса.

- [ARCH-MOD-007] [MUST] Любое разрешенное исключение существует только как узкое правило `[EXCEPTION]` в этой корневой конституции с причиной, областью, владельцем, проверкой и условием удаления. Plan-local отклонения запрещены.

- [ARCH-BE-001] Новый endpoint следует каноническому потоку допуска, чтения или записи. Исключения принимаются в корневом архитектурном контракте.

- [ARCH-BE-002] Контроллер передаёт управление use case. Для JSON ответ формирует Resource, для HTML используется Blade, для webhook — пустой HTTP-ответ.

- [ARCH-BE-003] [MUST] Action может владеть `DB::transaction` и планированием `afterCommit`; это не дает остальному application-коду право выполнять запросы.

- [ARCH-BE-004] [MUST] Job проектируется повторяемым и retry-safe. Он вызывает существующий Action/Service/repository вместо повторной реализации перехода.

- [ARCH-BE-005] [MUST] Resource получает уже загруженные данные и явно перечисляет публичные поля.

- [ARCH-BE-006] [MUST NOT] Route, Controller, FormRequest, Policy, Resource или Job строят Eloquent/SQL-запросы напрямую.

- [ARCH-BE-007] Eloquent, Query Builder и SQL принадлежат реализации repository в Infrastructure/Persistence. Конкретный read repository допустим для локального чтения. Контракт вводится на реальной границе модуля.

- [ARCH-BE-008] [MUST] Имя и API persistence-компонента выражают бизнес-намерение, а не набор универсальных CRUD-методов.

- [ARCH-BE-009] [MUST] Контракт располагается внутри владеющего доменного/application-модуля; реализация — в Infrastructure/Persistence и подключается контейнером Laravel.

- [ARCH-BE-010] [MUST NOT] Протаскивать Eloquent model/query builder за пределы persistence-границы или разрешать вызывающему слою дописывать запрос.

- [ARCH-BE-011] Прямой доступ разрешён в migrations, seeders/factories, тестах и узких bootstrap/diagnostic CLI. Исключение принадлежит владельцу backend и проверяется архитектурными тестами. При появлении продуктового сценария вынести запрос в repository.

- [ARCH-BE-012] [MUST] Транзакционная граница совпадает с одним бизнес-переходом и принадлежит Action либо специализированному application-компоненту.

- [ARCH-BE-013] [MUST] Внешняя сеть, тяжелый поиск и отправка уведомлений выполняются после commit, если не являются атомарной частью локальной записи.

- [ARCH-BE-014] [MUST] Job допускает повторную доставку, фиксирует устойчивый идентификатор операции и не полагается на состояние HTTP-запроса.

- [ARCH-BE-016] [MUST] Интеграция изолируется адаптером, когда ее протокол или поставщик не должны проникать в домен.

- [ARCH-BE-017] [MUST] Новые и изменяемые устойчивые многополевые бизнес-записи, пересекающие границы persistence, application и delivery, передаются через явно типизированные DTO. Форма передаваемого контракта не меняется мутацией исходного объекта или массива.

- [ARCH-BE-018] [MUST] Новый DTO неизменяем: `readonly` свойства имеют явные типы, вложенные значения состоят из скаляров, enum, других DTO или неизменяемых value objects. Eloquent model, Request, изменяемая Collection, сервис и контейнер не становятся свойствами DTO. Конкретный DTO объявляется `final readonly`, если ему не требуется обоснованное существующее наследование.

- [ARCH-BE-019] [MUST] DTO принадлежит модулю, владеющему данными. Одинаковые смысл и граница доступа используют один контракт; совпадение набора полей без совпадения смысла не требует общей базы, иерархии или универсального DTO.

- [ARCH-BE-020] [MUST] Persistence adapter преобразует загруженные модели в DTO, application создает новое выходное значение, а Resource явно перечисляет публичные поля. DTO не заменяет FormRequest validation, authorization, бизнес-инварианты или ограничения БД.

- [ARCH-BE-021] [MAY] Скалярные параметры, enum, типизированные списки и maps, локальные вычисления, действительно динамические внешние metadata и конечный массив сериализации не требуют DTO. Массив фиксированной бизнес-формы не используется вместо DTO на новой или изменяемой межслойной границе. Для частичного обновления отдельно сохраняется различие отсутствующего поля и `null`.

- [ARCH-BE-022] [MUST] Существующие контракты переводятся при изменении соответствующей границы вместе с ее непосредственными потребителями. Незатронутый legacy-код не требует массовой миграции, но не является образцом для нового контракта; необходимость DTO проверяется в архитектурном review.

- [ARCH-BE-023] [MUST] Новый или переводимый DTO называется с суффиксом `DTO` и располагается в каталоге и namespace `DTO` модуля-владельца. Суффикс и каталог `Data` для такого контракта не используются; незатронутый legacy-код переименовывается при изменении соответствующей границы по [ARCH-BE-022].

- [ARCH-AUTH-001] [MUST] Laravel владеет identity, session, CSRF, roles, permissions и окончательным решением об авторизации.

- [ARCH-AUTH-002] Клиент обращается к Laravel по одному origin и передаёт session cookie и CSRF для запросов изменения состояния.

- [ARCH-AUTH-006] [MUST] Каждый защищенный backend use case завершается Policy/Gate или эквивалентной серверной проверкой независимо от frontend guard.

- [ARCH-API-001] [MUST] Backend endpoint определяет явные request/response/error/privacy allowlists. Внутреннее поле модели не становится API автоматически.

- [ARCH-API-002] [MUST] OpenAPI генерируется из исполняемого backend-контракта и проверяется contract tests.

- [ARCH-ENF-001] [MUST] Новое правило границы сопровождается самой дешевой устойчивой автоматической проверкой: static restriction перед architecture test, architecture test перед широким end-to-end сценарием.

- [ARCH-ENF-002] Проверки документации подтверждают связь с исполняемым контрактом, данные моделей и пути источников. Валидатор плана проверяет форму и целостность evidence.

- [ARCH-SRC-002] [MUST] Долговечные решения о продукте, API и эксплуатации размещаются в профильных документах; временная хронология, task graph и evidence изменения — в tracked `plan/<feature-slug>-fast-tdd/`. Завершенный plan остается историческим доказательством и не заменяет runtime-код или профильную документацию.

- [ARCH-GOV-003] [MUST] Опубликованный `ARCH-*` ID не перенумеровывается, не переиспользуется для другого смысла и не удаляется, пока на него ссылается tracked plan или профильный документ. Семантически новое правило получает новый ID; уточнение без смены смысла сохраняет существующий ID.

## Документация и эксплуатация

- [ARCH-DOC-001] Инженерные источники находятся в [docs/backend](docs/backend/README.md), бизнес-сценарии — в [docs/flows](docs/flows/publish-calendar.md). Доступ сотрудников к Markdown и Scalar регулирует панель Filament.
- [ARCH-DOC-002] У процесса есть сценарии, правила, тестовый чеклист, следы, ошибки и критерии готовности. Запросы связаны с реальными operationId в генерируемом OpenAPI. Профильные документы описывают код и зависимости.
- [ARCH-API-006] При изменении контракта обновляются FormRequest/Resource, HTTP-тесты, OpenAPI и связанные страницы процесса. Версионированный JSON воспроизводится через Scramble.
- [ARCH-PERF-003] Утренние задания исполняются порциями с общим ограничением частоты, отложенным повтором при 429 и сохранением неоднозначного результата.
